# T-011 — Split the database roles and enforce the logging rule (I9)

## Description
Builds ADR 0002 §§ 10–11. `glucoscope_owner` owns the schema and is used only by the `db:*` scripts. `glucoscope_app` serves requests with row access only. Database errors are logged without values (invariant I9 becomes binding). **Blocks T-006** (any production deploy) **and any upload of real glucose data**, so the week-2 xDrip phone test uses synthetic readings until this lands (owner's decision, 2026-11-20).

## Acceptance criteria
Each criterion needs a named test, and every test runs in CI, except criteria marked *(review-checked)*. Those are checked in the build review instead.

**Roles**
- [ ] a new init script creates `glucoscope_owner` on fresh volumes
- [ ] for existing volumes, a documented one-time superuser step runs `REASSIGN OWNED BY glucoscope_app TO glucoscope_owner` in both `glucoscope` and `glucoscope_test` *(review-checked)*
- [ ] it is followed by a migration, safe to rerun, that grants `SELECT`/`INSERT`/`UPDATE`/`DELETE` and sequence `USAGE` on existing objects to `glucoscope_app`, and sets `ALTER DEFAULT PRIVILEGES FOR ROLE glucoscope_owner`
- [ ] CI's setup step also creates `glucoscope_owner`
- [ ] test on an **upgraded** database (schema v1 created under the single role, then handed over), not only a fresh one: no object in `public` is owned by `glucoscope_app` (checked against `pg_class` and `pg_namespace`)
- [ ] the role split: as `glucoscope_app`, `INSERT` into an identity-column table and into `session` succeeds, and `DROP TABLE` and `ALTER TABLE` fail
- [ ] if T-010 has already landed, the restore round trip is re-run with the split roles, and afterwards, as `glucoscope_app`, `SELECT` and `INSERT` still work and `DROP TABLE` still fails
- [ ] the app process never loads `MIGRATION_DATABASE_URL`

**Logging (I9)**
- [ ] the logging allowlist for the pool listener, `errorHandler` and the runner
- [ ] database errors are detected with `err instanceof pg.DatabaseError`, not by checking for a `code` property
- [ ] a non-database error that carries a database message is not logged verbatim
- [ ] I9 also covers `checkConnection` (`src/models/db.js:20`, which logs `err.message` today) and `waitForDatabase` from T-009, including the messages it throws that `server.js` prints
- [ ] `contracts.md` § 5 (`checkConnection` "logs `err.message` only") and `test/db.test.js` are updated to match I9

**Docs**
- [ ] `contracts.md` § 7 (`MIGRATION_DATABASE_URL` and its separate env file) *(review-checked)*
- [ ] I9 changes from planned to binding *(review-checked)*

## Out of scope
- Production role setup on the server (T-006).
- Where logs go and how long they are kept (T-006).

## Risks / dependencies
- Depends on T-009.
- T-010 can land before or after this task. Whichever lands second re-runs the restore round trip with the split roles.
- Blocks T-006 and any upload of real glucose data. **Gate, not a testable criterion:** no real glucose data is uploaded to any database before this task lands. The week-2 xDrip phone test uses synthetic readings.
- Needs the owner to run one documented superuser command on their existing Docker volume.
