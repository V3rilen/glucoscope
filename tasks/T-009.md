# T-009 — Build the migration runner, seeds, test database and CI Postgres

## Description
Builds ADR 0002 §§ 1–5, 7 and 8: the `db:migrate` runner, `seed.sql`/`seed-test.sql`, `db:seed`, `db:reset`, the `test:db` suite and its guards, and PostgreSQL in CI. It replaces `database/setup.js` and `db:setup` from the owner's unmerged `wip/database-setup` branch, and carries over the reviewed fixes stashed against that branch. **Blocks schema v1** (the first real tables). Until T-010 lands, `db:migrate` takes no backup; that is acceptable because no production data can exist before T-006.

## Acceptance criteria
Each criterion needs a named test, and every test runs in CI, except criteria marked *(review-checked)*. Those are checked in the build review instead.

**Runner**
- [ ] refusal on a checksum mismatch
- [ ] a failed file rolls back and records nothing
- [ ] the `no-transaction` header
- [ ] the advisory lock blocks a second run
- [ ] a `-- migrate:destructive` file is refused without `--confirm-destructive`

**Seed data**
- [ ] `seed.sql` run twice changes nothing
- [ ] an edited `site_settings` row is kept, and a renamed event type is not recreated
- [ ] `seed.sql` has no `users` or `session` inserts
- [ ] plain `db:seed` never loads `seed-test.sql`
- [ ] refusals for `db:seed --test` and `db:reset`: on production, on an unset or other `NODE_ENV`, on a database not on the allowlist, and on reset without `--yes`

**Test database**
- [ ] the `test:db` name guards, with one negative test each

**Workflow**
- [ ] the `package.json` scripts match ADR 0002 and the T-005 plan's npm scripts table. `db:setup` and `database/setup.js` are removed, and the README says an old dev database must be rebuilt with `db:reset --yes` (which deletes its data). *(review-checked)*
- [ ] every refusal message from the runner, seeds, reset and test guards names the next step for the maintainer

**CI**
- [ ] CI runs `test:db` in the `scripts` job, with `NODE_ENV=test`, using the digest-pinned `postgres:17.x` service. T-008's guard is extended to cover `test:db`.
- [ ] A CI setup step creates a **non-superuser** role that matches the wip `01-create-app-user.sh` (NOSUPERUSER NOCREATEDB, owns `public`), and `test:db` runs as that role, never as the service's superuser.

**Docs**
- [ ] `contracts.md` § 5 (the `withClient()` export), § 7 (`TEST_DATABASE_URL`) and § 10 are updated *(review-checked)*
- [ ] `data-model.md` § 2 gets each table as it lands *(review-checked)*

**Carry-over**
- [ ] each of the ten stashed review fixes is accounted for:
  - #1 (connection timeout), #2 (permanent errors fail fast) and #4 (TCP healthcheck) are carried into `db.js`, `server.js` and the compose file
  - #3 (password-change note) is carried into the README
  - #5 (crash-safe rollback) is carried into the runner, which replaces `setup.js`
  - #7–#10 (schema constraints) go into 0001 with schema v1
  - #6 was a false finding, so there is nothing to carry

## Out of scope
- Backup before migrating and `db:restore` (T-010).
- The owner/app role split and logging invariant I9 (T-011).
- Schema v1 itself (0001 and the app tables): its own task, after this one. It is reviewed against the Data Engineer redlines, not copied from the wip `schema.sql`. Inputs from the T-005 review:
  - the wip schema has six foreign-key columns with no index: `users.role_id`, `events.event_type_id`, `care_link_history.changed_by`, `day_comments.author_id`, `support_tickets.assigned_to` and `ticket_messages.author_id`
  - `users.upload_secret_hash` stays out of 0001 until the B4 threat model is done (`docs/architecture.md` § 2)

## Risks / dependencies
- Input: branch `wip/database-setup` and the stash `review fixes for DB setup (#1-#10)`.
- Blocks: schema v1, T-010, T-011.
- Touches `.github/` (the CI service and `test:db` step), which must be named in the PR summary.
