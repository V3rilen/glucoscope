# T-006 — Deployment and rollback procedure

## Description
`docs/architecture.md` § 2 and § 7 and `docs/data-model.md` § 1 record the deployment facts as `UNKNOWN`, because nothing in the repo shows them. **The owner decided on 2026-11-17 (T-001) that there is no production deploy until this task lands.** Opened by the T-001 docs bootstrap.

## Acceptance criteria
- [ ] Record the Cloudflare-to-origin link (Tunnel or proxied DNS with port forwarding), the SSL mode, and whether the origin accepts only Cloudflare traffic. If the origin is reachable directly, address the `X-Forwarded-*` forgery risk created by `trust proxy`.
- [ ] Record Cloudflare cache and WAF rules, including that they must not cache pages and must not block xDrip+ POSTs to `/api/v1/*` (`PROJECT_PLAN.md` § 8).
- [ ] Record that PostgreSQL listens on localhost only, the app role's privileges (from T-011: `glucoscope_app` has row access only; `glucoscope_owner` owns the schema), and whether Express-to-PostgreSQL TLS is needed.
- [ ] Record the process manager (system service or PM2), how `NODE_ENV=production` and the `.env` file are provided, and where logs go.
- [ ] Record the release steps and a **rollback procedure that has been tested**, including migrations. T-005 decided the approach ([ADR 0002](../docs/decisions/0002-database-migrations.md)):
  - forward-only migrations
  - the default rollback is the app, not the database
  - deploy order: `db:migrate` (takes a backup first), then `db:seed`, then restart the app
- [ ] Record the production **restore runbook**:
  1. stop the app
  2. `npm run db:restore -- --file <name> --yes`
  3. deploy the release that matches the migration version it prints
  4. start the app

  Test it once against a copy of production.
- [ ] Record the **loss window**: data written between the pre-migration backup and the restore is lost. The owner accepted this in T-005 (`tasks/T-005.md` activity log, 2026-11-20). They chose the full backup ("1. okay lets go with option C.") and then approved plan v5.1, which states this loss window ("That sounds good. i approve").
- [ ] Record where `BACKUP_DIR` lives on the server (outside the repo, not under `/tmp`, mode 700) and how backups are protected off the machine. They are a sensitive store: every user's PII and health data.
- [ ] Record how production gets a PostgreSQL 17 `pg_dump`/`pg_restore` client (`PG_CLIENT_CMD`).
- [ ] Record where `MIGRATION_DATABASE_URL` lives on the server: a mode-600 env file loaded only by the `db:*` scripts, never by the app.
- [ ] Record backups: a scheduled `pg_dump`, stored off the machine, with at least one test restore.
- [x] Record whether the CI checks are required on `main` (branch protection). Done in T-004 (`docs/architecture.md` § 7): ruleset `protection-main`.
- [ ] Record which Node.js version production runs (CI tests the `engines` floor, 22.9.0; added by the T-004 review).
- [ ] Record any uptime monitor pointed at `/health`, and where logs are kept and for how long.
- [ ] The `/health` hang when the DB host is unreachable (no `connectionTimeoutMillis`; `PGCONNECT_TIMEOUT` has no effect) is a **code change**. It needs its own plan and tier, and a regression test showing that an unreachable DB returns 503 within a bounded time. It may be split into its own task. **2026-11-20:** T-009 carries the reviewed fix from the owner's database work; this item closes when T-009 lands with that test.
- [ ] Update `docs/architecture.md` and `docs/data-model.md`, replacing each `UNKNOWN`. This is a `/docs` edit, so it needs 6-agent consensus.
