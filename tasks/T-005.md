### Decisions
1. **Tool: 1A (owner's choice).** Plain numbered `.sql` files run by a small in-repo runner on the existing `pg` driver. No new dependency. Rejected: `node-pg-migrate`, a new dependency. The Architect confirmed neither `node-pg-migrate` nor `connect-pg-simple` is installed today.
2. **Layout.**
   - Files are `database/migrations/NNNN_short_snake_name.sql`: four digits, sequential, never reused.
   - The `schema_migrations` table records version, file name, SHA-256 and applied_at.
   - An applied file is **never edited**. The runner refuses to run on a checksum mismatch.
   - Each file runs in its own transaction. The **only** exception is a file whose first line is `-- migrate:no-transaction`, for `CREATE INDEX CONCURRENTLY`. Such a file holds exactly one statement and is Risky tier with Data Engineer sign-off.
   - The folder note in `PROJECT_PLAN.md` § 13 becomes `database/ # migrations/, seed.sql, seed-test.sql`, replacing `schema.sql`, as the owner chose. The wip `schema.sql` becomes `0001_initial_schema.sql` (minus the default rows, which move to `seed.sql`).
3. **Reversibility and recovery (owner's choice C: full backup).**
   - Migrations are **forward-only**. Mistakes are fixed with a new migration.
   - **The default rollback is the app, never the database.** Migrations follow expand-then-contract, so the previous release still runs on the new schema.
   - **Last resort:** restore the full backup taken just before migrating (decision 4). It returns the **whole database** to its state before the migration, with every table and the original IDs.
   - **Loss window:** anything written between the backup and the restore is lost, for example CGM uploads, entries and comments.
     - The window lasts **from the backup until the restore**, so it grows with how long a problem takes to notice.
     - Before it accepts `--yes`, `db:restore` shows the backup's age, for example "taken 3 h 12 min ago; data written since then will be lost".
     - After restoring, it prints the next step: "The database is at migration NNNN. Deploy the release that matches it before starting the app."
   - The ADR quotes the Data Engineer redlines as binding migration rules:
     - no destructive change without a deprecation plan and a forward fix,
     - no `NOT NULL` on a populated column without a tested backfill,
     - no foreign-key column without an index.
   - **Migrations never depend on rows from `seed.sql`,** because seeding runs after migrating. A backfill that needs a role or an event type inserts that row itself with `ON CONFLICT DO NOTHING`.
   - A destructive file says so in its header (`-- migrate:destructive`). `db:migrate` refuses to run it unless `--confirm-destructive` is passed.
4. **Running.**
   - Migrations run only through `npm run db:migrate`, **never on app startup**.
   - **Deploy order:**
     1. `db:migrate`, which takes the backup first
     2. `db:seed`
     3. app restart (T-006)
   - The runner holds a **session-level** `pg_advisory_lock` on one dedicated client for the whole run. `db.js` exports a `withClient()` helper (a contract change, `contracts.md` § 5, in T-009).
   - With the role split, `db:migrate`, `db:seed`, `db:restore` and `db:reset` connect through `MIGRATION_DATABASE_URL`, the schema owner.
     - It lives in a **separate mode-600 env file that only the `db:*` scripts load**, never in `.env`, so the app process never holds schema-owner credentials.
     - The app uses `DATABASE_URL`. Both are recorded in `contracts.md` § 7 in T-011. Until T-011 lands, the `db:*` scripts use `DATABASE_URL`, with the single wip role.
   - Every refusal message tells the maintainer what to do next.
   - **The backup:**
     - When there are pending migrations and the database is not empty, `db:migrate` first runs `pg_dump --format=custom`, which is a consistent snapshot.
     - **If the backup fails, no migration runs.** No backup is taken when nothing is pending.
     - **Client tools:** the client (`pg_dump`, `pg_restore`) must be at least the server's version (17). The command used is configurable (`PG_CLIENT_CMD`, recorded in `contracts.md` § 7):
       - **Dev:** the dev host has no PostgreSQL client, so the tools run inside the compose container (`docker compose exec -T db …`). The runner streams the output into the file it created itself.
       - **CI:** the tools come from the same digest-pinned `postgres:17.x` image, or from a pinned `postgresql-client-17`.
       - **Production:** T-006.
       - The tests check `pg_dump --version` is 17 or newer and **fail, never skip**, if it isn't.
     - **Credentials are passed only through `PG*` environment variables, never on the command line,** where `ps` and Node's `err.cmd` would show them. A tool failure logs only its exit code.
   - **Backup files hold all PII and health data**, so they are classified **sensitive** in `architecture.md` § 2 and `data-model.md` § 5.
     - They live in `BACKUP_DIR`. That directory must be outside the repo and must not be under `/tmp`.
       - The runner checks this **after resolving symlinks** (`realpath`).
       - It creates the directory with mode 700 and refuses to use it if it is group- or world-accessible.
       - `db:restore` repeats every one of these checks.
     - Each file is created exclusively with mode 600, whatever the umask. It is named by timestamp, a sequence number and the migration version, so two backups in the same second never collide. Files are never overwritten.
     - **Privacy:** a deleted account's data stays in backups until the newest 5 have rotated past it. This is recorded in `data-model.md` § 5.
     - **Retention:** keep the newest 5. Older files are deleted only after the new backup has been verified (`pg_restore --list` succeeds).
     - Backup contents and paths are never logged beyond the file name.
   - **`npm run db:restore -- --file <name> --yes`** restores a backup.
     - It shows the backup's timestamp and version, and refuses without `--yes`.
     - It refuses while any other session is connected (it checks `pg_stat_activity`), so the app must be stopped first.
     - It holds the advisory lock.
     - It runs `DROP SCHEMA public CASCADE; CREATE SCHEMA public` as the schema owner, then `pg_restore --single-transaction` (without `--clean`). Tables the bad migration created can't survive.
     - It only accepts files from `BACKUP_DIR` and never runs a file as SQL text.
     - This is the production recovery command, and T-006 documents the runbook around it.
5. **Seed data (owner left this to the plan; Coordinator's choice).**
   - **Default data goes in `database/seed.sql`:** roles, the single `site_settings` row, and the starting event types.
     - It runs in **every** environment, production included, through `npm run db:seed`, after `db:migrate`.
     - It is safe to rerun. Roles and `site_settings` use `ON CONFLICT DO NOTHING`. Event types are inserted **only when `event_types` is empty**, so an event type an admin has renamed or deleted is not recreated.
     - Code looks these rows up **by name, never by ID**.
     - It never touches `users` or `session` and holds no credentials.
   - **Test data goes in `database/seed-test.sql`:** test accounts and sample readings. It runs through `npm run db:seed -- --test`.
     - It is kept separate so that **test accounts with known passwords can never reach production**.
   - `db:seed --test` and `db:reset` refuse unless all of these hold:
     - `NODE_ENV` is `development` or `test`,
     - the connected `current_database()` is on the dev allowlist (`glucoscope`, `glucoscope_test`),
     - and, for `db:reset`, `--yes` is passed. The reset deletes all data.
     - Because the production database may also be named `glucoscope`, the `NODE_ENV` check is what blocks production.
   - Whether the rubric's test accounts may exist in production is decided by the auth task (week 2). Until then, the default is **no**.
6. **Backfills.**
   - A backfill runs inside the migration transaction **except** on `glucose_readings` and `events`. `glucose_readings` alone grows by about 105k rows per user per year.
   - On those two tables, backfills run as batched updates outside the transaction, with a progress check and Data Engineer review.
7. **PostgreSQL version.**
   - The app targets **PostgreSQL 17**. The owner's dev container reports **17.11** (`postgres --version`, 2026-11-19).
   - T-009 pins the same minor version in compose and CI. CI pins it by digest.
   - The production version is `UNKNOWN` (T-006).
8. **Test database.**
   - The database tests live in `test-db/`, outside the `npm test` glob. They run with `npm run test:db` (`--test-concurrency=1`, **without** the `test/setup.js` tripwire) against `TEST_DATABASE_URL`.
   - Before any `DROP`, the runner checks four things:
     - the database name parsed with `pg-connection-string` is `glucoscope_test`,
     - `TEST_DATABASE_URL` is not the same as `DATABASE_URL`,
     - `NODE_ENV` is not `production`,
     - and, after connecting, `SELECT current_database()` returns `glucoscope_test`.
   - Each file starts from a fresh schema (drop, then migrate).
   - `glucoscope_test` is created by a second init script for new volumes. For existing volumes, a documented one-time command does it: `CREATE DATABASE glucoscope_test OWNER …`.
   - In CI, a `postgres:17.x` service pinned by digest and a `test:db` step go in the **required `scripts` job**. The service password is labelled a throwaway non-secret. T-008's guard is extended to cover `test:db`.
9. **The `session` table.**
   - A migration creates it from the installed `connect-pg-simple` version's `table.sql`, and `createTableIfMissing` stays off.
   - Its `timestamp(6)` column without a time zone is recorded in `data-model.md` § 2 as a library-mandated exception to the TIMESTAMPTZ rule.
10. **Logging errors (security, planned invariant I9, binding from T-011).**
    - For a PostgreSQL `DatabaseError` (one that has `code`), log **only** `code`, `constraint`, `table`, `column`, `routine` and a query or request label.
    - **Never** log `message`, `detail`, `hint`, `where`, `position`, `stack` or the error object itself. PostgreSQL messages repeat input values, for example `invalid input syntax for type integer: "<value>"`.
    - This applies to the pool listener (`db.js:7`), `errorHandler.js` and the runner's own output.
11. **Database roles (security).**
    - Default: **split in T-011**. `glucoscope_owner` owns the schema and runs migrations. `glucoscope_app` gets data access only (`SELECT`/`INSERT`/`UPDATE`/`DELETE`), through `ALTER DEFAULT PRIVILEGES`. With one role, a SQL injection could `DROP` or `ALTER` tables.
    - **Settled:** the owner's choice to split the build (2026-11-20) answers call 2. The roles are split in T-011, which blocks every production deploy. There is no longer a path that defers the split.

**T-010: backup and restore** (`tasks/T-010.md`, depends on T-009)
- *Backup*
  - a backup is taken only when migrations are pending and the database is not empty
  - a failed backup stops `db:migrate` before any file runs
  - the `BACKUP_DIR` checks: the directory is mode 700, files are mode 600 and never overwritten, and a world-readable directory is refused
  - `BACKUP_DIR` is refused inside the repo, under `/tmp` and through a symlink. The test fixtures never use `/tmp`.
  - retention keeps the newest 5, and only after the new backup is verified
  - two backups in the same second both succeed
- *Restore*
  - restore round trip: back up, run a migration that both creates a table and alters `users`, then restore. Every table matches, the new table is gone, and a new `INSERT` into `users` works.
  - `db:restore` refuses: without `--yes`, on files outside `BACKUP_DIR`, and while another session is connected
  - restore uses `pg_restore --no-owner`, so a backup taken before T-011 (which records the owner as `glucoscope_app`) restores cleanly
  - if T-011 has already landed, the round trip is re-run with the split roles
  - `db:restore` shows the backup's age before confirming, and prints the matching migration version afterwards
- *Client tools*
  - the client version check fails when `pg_dump` is older than 17, and CI runs these tests with the PG 17 client. T-008's guard is extended to that CI step.
  - a failed `pg_dump` or `pg_restore` logs no URL and no password, only its exit code

### Lenses (major decision)
- **Value and cost:** no new dependency. Backups use a few MB of disk each, and 5 are kept. The cost is building and testing the runner (T-009), backup and restore (T-010) and the role split (T-011).
- **User:** nothing changes day to day. If a migration goes badly, patients and caregivers get their full history back from the backup, except data written between the backup and the restore. Logging rule I9 keeps their health data out of the logs.
- **Maintainer:** plain SQL that the owner can read, plus enforced checksums and refusal messages. The cost is owning the runner's tests.
- **Scope and timing:** the build is split three ways, as the owner chose. Schema v1 waits only on T-009. T-010 and T-011 run alongside it and must land before any production deploy.
- **Conflict:** Maintainer and Security both favour splitting roles now, which pulls against Scope and timing. Surfaced to the owner as call 2. Option B (copying accounts only) was dropped: making its restore correct cost more than a full backup and protected less.
