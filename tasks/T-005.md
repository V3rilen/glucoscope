# T-005 — Migration tooling and conventions

## Description
`docs/data-model.md` § 6 records the migration approach as `UNKNOWN`. Before the first table (week 2, `PROJECT_PLAN.md` § 13), decide how the schema is created and changed. Opened by the T-001 docs bootstrap.

## Acceptance criteria
- [ ] Choose the tool: plain numbered SQL files with a small runner, or a migration library (a new dependency, which is Risky tier). Record the choice as an ADR.
- [ ] Define the directory, naming convention, up/down (reversibility) rules, how migrations run at deploy time, the seed-data approach, and the backfill expectations.
- [ ] Record the PostgreSQL server version the app targets.
- [ ] Decide how DB integration tests get a disposable database.
- [ ] Decide who creates `connect-pg-simple`'s `session` table: a migration, or the library's `createTableIfMissing`. It lands with schema v1 in week 2 (`PROJECT_PLAN.md` § 13).
- [ ] Decide which query errors may be logged in full, since full error objects are logged today (`docs/architecture.md` § 2, "Logs may contain sensitive data").
- [ ] Update `docs/data-model.md` § 1 and § 6. This is a `/docs` edit, so it needs 6-agent consensus.

## Risks / dependencies
- T-006 (rollback) depends on this, because whether migrations can be reversed decides how a release can be rolled back.
